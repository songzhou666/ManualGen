# AUDIT + JUDGE 阶段详情

---

## AUDIT 阶段

**职责**：对照6维度质量体系对 `_integration.md` 做初次评分，准备审核报告。

> 注意：AUDIT 阶段是主 Agent 的自我评分，用于快速发现问题。
> **JUDGE 阶段会拉起真正独立的子 Agent 做最终盲审**——那才是真正的质量门。

### 执行流程
1. 加载 `_integration.md`（完整手册文件）
2. 对照下方6维度检查清单逐项打分
3. 生成 `_audit.md` 输出报告

### 🚨 强制执行规则（违反=审核无效）

**规则1** → 不得使用"五星评分"、"★☆☆☆☆"等简化评分方式
- 必须按下方6维度表格逐项打分，每项给出0~100的具体数值
- ❌ **禁止** `★★★★★` 这种评级
- ✅ **必须** 用 `85/100` 这种具体数值

**规则2** → 每个维度的评分必须附上**具体理由**
- 正例：`④ 操作可执行性：65/100 → 原因：缺少字段说明表，操作结果描述不完整`
- 反例：`可执行性：良好 ✅`（太模糊，无效）

**规则3** → 阻断检查**必须逐项列出结果**，不得跳过
- 必须输出完整的阻断检查表，每项标注✅通过或❌阻断

**规则4** → 评分必须基于产出物的**实际内容**，而非"模板声称"
- 不要只看模板里写了什么，要看**最终产物里实际有什么**
- 例如：如果 `_integration.md` 中没有流程图，即使模板声称"包含流程图"，评分也应扣分

**规则5** → 综合评分计算公式必须可追溯
- 每维度分 × 权重 的加权和 = 综合分
- 必须在 `_audit.md` 中展示计算过程

### 六维度质量检查（对标优秀用户手册标准）

| 维度 | 权重 | 检查要点 |
|:-----|:----:|:---------|
| **① 手册结构完整性** | 25% | 逐项核对7大必备模块是否齐全：<br>1. 手册前置说明（概述/版本/名词释义/环境/联系方式）✅<br>2. 系统基础操作（账号/页面/通用规则+流程图）✅<br>3. 核心业务功能（按用户使用频率排序，每模块含8项标准结构）✅<br>4. 全流程业务闭环（跨角色全局泳道图）✅<br>5. 异常问题与故障处理（报错汇总/边界/紧急流程）✅<br>6. 权限与角色对照表（矩阵+权限流转图）✅<br>7. 附则与更新说明（约束/日志/Q&A）✅ |
| **② 流程图质量** | 20% | 按流程图专属规范逐项检查：<br>1. 分类绘制：单功能用线性图，复杂用分支图，角色流转用泳道图 ✅<br>2. 节点通俗：流程节点使用用户语言，无技术术语 ✅<br>3. 链路完整：包含正常/驳回/终止/异常走向，无断点 ✅<br>4. 标注清晰：必填项、高危操作、角色归属、时效限制已标注 ✅<br>5. 一一对应：每个核心功能/核心场景必有对应专属流程图 ✅ |
| **③ 去技术化合规性** | 15% | 全程无技术内容：<br>1. 无API端点表格（如 `\| POST /api/xxx`）✅<br>2. 无HTTP代码示例（如 `\`\`\`http`、`curl` 命令）✅<br>3. 无后端服务名/数据库名/底层原理堆砌 ✅<br>4. 操作描述基于界面操作而非API调用 ✅<br>5. 只讲"用户怎么做、做什么、不能做什么" ✅ |
| **④ 操作可执行性** | 15% | 按核心业务功能8项标准检查：<br>1. 功能简介：一句话说明用途和适用场景 ✅<br>2. 权限说明：哪些角色可操作/仅查看/无权限 ✅<br>3. 前置条件：操作前必须完成的步骤和条件 ✅<br>4. 分步操作：1/2/3数字步骤引导 ✅<br>5. 字段说明：必填/规则/格式/示例完整 ✅<br>6. 操作结果：成功标志+数据变化+后续走向 ✅<br>7. 风险提示：高危操作醒目警示+标注不可逆操作 ✅ |
| **⑤ 角色隔离与权限清晰** | 15% | 角色权限检查：<br>1. 每个功能模块标注了可操作的角色 ✅<br>2. 有全局角色权限矩阵表（增/删/改/提交/审核/导出/查看）✅<br>3. 权限流转图（权限生效/变更/回收）✅<br>4. 不同角色的操作流程不混写，角色边界清晰 ✅<br>5. 用户能判断"我能不能操作这个功能" ✅ |
| **⑥ 异常覆盖完整度** | 10% | 异常处理检查：<br>1. 常见报错汇总：报错文字→产生原因→解决步骤一一对应 ✅<br>2. 操作异常处理：提交失败/审核驳回/流程卡死等场景 ✅<br>3. 边界问题说明：不支持的操作/数据不可修改/流程不可回退 ✅<br>4. 紧急处理流程：重大错误的应急步骤+反馈渠道 ✅ |

### 🚨 阻断性检查（任何一项不通过→整体不通过）
| 检查项 | 检查方式 | 阻断条件 |
|--------|---------|----------|
| 隐私安全 | 扫描所有产物中的密码/密钥/IP | 发现任何明文密码/密钥 → 阻断 |
| 流程图合规 | 验证Mermaid语法使用 | 有任何文字图替代Mermaid → 阻断 |
| 流程图完整性 | 检查用户手册中每个模块是否包含≥1个Mermaid流程图 | 存在无Mermaid流程图的模块 → 阻断 |
| 内容合规性 | 扫描用户手册中的API端点/HTTP代码示例 | 发现 `| POST/GET/PUT/DELETE`、````http` 或 `curl` → 阻断 |
| TODO占位内容 | 检查是否有未解决的TODO:PLACEHOLDER标记 | 发现未解决的PLACEHOLDER → 阻断（TODO_RESOLVE阶段处理后仍存在的才阻断） |
| 状态图合规 | 检查stateDiagram-v2格式 | 状态图非Mermaid格式 → 阻断 |
| 模板块数验证 | 验证声称数vs实际列数 | 声称N个但列出M个(M<N) → 阻断 |
| 合并完整性 | 检查整合产物是否外部文件引用 | 包含"详见 X.md""参见 _modules/"类引用 → 阻断 |
| 文件命名 | 检查最终文件是否按项目命名 | 不是 `{项目名} 用户操作手册.md` 格式 → 阻断 |
| 文件位置 | 检查最终文件是否在项目根目录 | 在 `.agent/harness/` 内 → 阻断 |

**执行方式**：这些检查项由AUDIT阶段强制执行，**不能自动跳过**。

### 检查点
- ① 手册结构完整性 ≥ 80%（7大模块缺失 ≥ 2个 → 直接阻断）
- ② 流程图质量 ≥ 80%
- ③ 去技术化合规性 ≥ 80%（发现API端点 → 直接阻断）
- ④ 操作可执行性 ≥ 75%
- ⑤ 角色隔离与权限清晰 ≥ 75%
- ⑥ 异常覆盖完整度 ≥ 75%
- 综合评分 ≥ 85%（否则返回 WRITE 修复）

### 产物
`_audit.md`（详见 `artifacts/template-artifacts.md` 2.6）

## JUDGE 阶段

**职责**：使用完全独立的子 Agent 进行盲审，判定文档是否可发布。

### 第 1 步：拉起独立子 Agent 进行盲审（强制 — 核心质量门）

这是最关键的一步。**你必须拉起一个全新的子 Agent 来做审核，不得自己审核自己。**

使用 `Task` 工具的 `general_purpose_task` 子 Agent，query 参数中只传入以下信息：

```
你是一个完全独立的质量评审官。你与文档编写过程完全隔离。
你不知道这个系统是做什么的，不知道谁写了这个文档，不知道文档经过了哪些阶段。

你的输入只有：
1. 文件路径：{项目根目录}/{项目名称} 用户操作手册.md（最终交付件）
   如果找不到，尝试 .agent/harness/_integration.md（中间件）
2. 下方的 6 维度检查清单

请按以下步骤执行：

第 1 步：读取最终交付文件（优先读取项目根目录下的 `{项目名称} 用户操作手册.md`，找不到则读 `.agent/harness/_integration.md`）
第 2 步：对照 6 维度检查清单逐项打分（只看实际内容，不看标题名称）
第 3 步：给出综合评分和最终判定

6 维度检查清单：
① 手册结构完整性（满分25分）：
   检查以下 7 个章节是否存在：前置说明（概述/版本/名词释义/环境/联系方式）、
   基础操作（账号/页面/通用规则+流程图）、核心功能（按8项标准）、
   业务闭环（全局泳道图+角色标注）、异常处理（报错/边界/紧急）、
   权限角色（矩阵+流转图）、附则（约束/Q&A）
   评分：7全有=25，缺1个=20，缺2个=阻断(10分)，缺≥3个=阻断(0分)

② 流程图质量（满分20分）：
   检查 Mermaid 流程图：全文≥3个流程图、分类正确、节点用用户语言、
   链路含正常+驳回+终止走向、无ASCII文字图替代
   评分：无Mermaid图=0分(阻断)，有ASCII图替代=10分，逐项扣减

③ 去技术化合规性（满分15分）：
   禁止出现：API端点表(| POST /api/)、HTTP代码块(```http)、
   后端名/数据库名(Python/SQLite/Neo4j)、无解释的技术术语(RAG/LLM/Top-K)、bash命令
   评分：发现任意1项=0分(阻断)，全无=15分

④ 操作可执行性（满分15分）：
   随机抽3个模块检查：功能简介、权限说明、前置条件、分步操作、
   字段说明(必填/格式/示例)、操作结果、风险提示
   评分：7项全=15，缺1项=12，缺2项=8，缺≥3项=0

⑤ 角色隔离与权限清晰（满分15分）：
   检查：每模块标注角色、全局权限矩阵表(增/删/改/提交/审核/导出/查看)、
   权限流转图、角色不混写、用户能判断权限
   评分：5项全=15，缺1项=10，缺≥2项=0

⑥ 异常覆盖完整度（满分10分）：
   检查：报错汇总表、操作异常处理、边界说明、紧急处理流程
   评分：4项全=10，缺1项=5，缺≥2项=0

阻断条件（任意一条=整体不通过）：
- 结构完整性缺≥2个模块 → 阻断
- 无任何Mermaid流程图 → 阻断
- 发现API/HTTP/技术名词堆砌 → 阻断
- 发现任何"详细操作请参阅 xxx.md"或`_modules/`引用 → 阻断（必须完整内联）

最终判定：
- 综合≥85分 → PASS 可交付
- 75~84分 → CONDITIONAL PASS 需微调
- 60~74分 → FAIL 需修复
- <60分或阻断 → FAIL 需重写

输出格式（严格遵循，返回纯文本）：
========================================
[SCORE] 综合分: {分数}/100
[VERDICT] {PASS/CONDITIONAL_PASS/FAIL}
[BLOCKER] {有/无}
--- 各维度得分 ---
① 手册结构完整性: {分}/25
② 流程图质量: {分}/20
③ 去技术化合规性: {分}/15
④ 操作可执行性: {分}/15
⑤ 角色隔离与权限清晰: {分}/15
⑥ 异常覆盖完整度: {分}/10
--- 主要问题 ---
{列出每个不合格的原因}
========================================
```

子 Agent 的返回结果就是最终判定依据，**你必须将其写入 `_judgment.md` 作为最终判定报告**。

### 第 2 步：处理审核结果

根据子 Agent 的返回结果：

- `[VERDICT] FAIL` 且 `[BLOCKER] 有`：
  → **自动判定为不通过** → 回到 WRITE 修复

- `[VERDICT] FAIL` 且 `[BLOCKER] 无`：
  → 根据各维度得分，针对性修复低分项 → 回到 WRITE

- `[VERDICT] CONDITIONAL_PASS`：
  → 人工判断是否可接受

- `[VERDICT] PASS`：
  → 进入正常判定流程

### 第 3 步：最终判定

正常判定流程：
- **PASS**（综合≥85% 且无阻断）→ DONE
- **CONDITIONAL PASS**（≥75% 但有阻断）→ 等待用户判断
- **FAIL**（<75%）→ WRITE修复

### 修复流程
```
WRITE(修复) → INTEGRATE(重新整合) → AUDIT(重新审核) → JUDGE(重新判定)
```
- 禁跳过中间步骤
- 最多2次重试
- retry ≥ 2 → FAILED（流程终止，需人工介入）

### 产物
`_judgment.md`
