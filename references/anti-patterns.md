# ManualGen 反模式说明

> 收集常见错误用法案例，帮助用户避免典型陷阱。
> 每个案例包含：现象 → 根本原因 → 正确做法 → 改进对比。

---

## 反模式 1：零散需求直接生成（跳过 EXPLORE）

### 现象

用户提供零散的、不完整的需求描述（如"帮我写个用户管理的手册"），AI 未执行 EXPLORE 阶段就直接进入 EXTRACT，导致生成的产物与项目实际业务流程脱节。

### 为什么是反模式

ManualGen 的 EXPLORE 阶段负责理解项目业务全貌（架构、模块、角色、流程）。跳过这一阶段意味着：
- 不知道系统有哪些功能模块
- 不理解数据依赖关系和创建顺序
- 不了解用户角色划分和权限边界

直接提取信息会导致"只见树木不见森林"，生成的手册与实际业务严重不符。

### 正确做法

- 提供项目路径和简要需求即可
- AI 必须执行入口清单 → 进入 EXPLORE 阶段扫描项目
- 等待 EXPLORE 阶段的探索报告输出后再决定下一步

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 启动方式 | "帮我写用户管理手册" | "帮我生成这套系统的操作手册" |
| EXPLORE | 跳过 | 自动执行，扫描项目全貌 |
| 产出质量 | 与项目实际脱节 | 基于真实业务分析 |

## 反模式 2：一次性加载所有模块（忽略分批）

### 现象

在大型项目（>200文件）中，AI 试图在一次 ANALYZE 阶段分析所有模块，导致上下文超载、分析不完整或遗漏关键功能。

### 为什么是反模式

AI 的上下文窗口有限。一次性加载过多模块会导致：
- 每个模块只能浅层分析，无法深入
- 模块间关系梳理不完整
- 需要反复确认，效率下降

### 正确做法

- 让 AI 自动使用分批分析机制
- 每批 3-5 个模块，分批产出 `_analysis.md` + `_function_survey.md`
- 批次间自动传递上下文，使用 `_analysis_batch_index.md` 管理索引

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 分析范围 | 所有模块一次分析 | 每批 3-5 个模块 |
| 分析深度 | 浅层扫描 | 深入每个模块的业务流程 |
| 大型项目 | 上下文超载 | 分批可控 |

## 反模式 3：跳过 GAP 阶段直接进入 WRITE

### 现象

ANALYZE 完成后，AI 直接进入 WRITE 阶段开始写模块文档，跳过了 GAP（完整性评估）阶段。

### 为什么是反模式

GAP 阶段负责：
- 评估功能完整性（哪些功能已实现/部分实现/缺失）
- 识别数据流断点
- 生成项目形状报告
- 给出完整性综合评分

跳过 GAP 意味着不知道文档覆盖是否完整，写了半天发现关键模块遗漏。

### 正确做法

- ANALYZE 完成后，AI 自动进入 GAP 阶段
- GAP 阶段产出 `_gap_analysis.md`（完整性评估 + 项目形状报告）
- GAP 完成后由 AI 自主进入 AUTO_REVIEW（不中断等用户），输出「缺失清单 + 完整性评分」到 `_auto_decisions.md`；
- AUTO_REVIEW 决策后自动推进到 RESOLVE/WRITE（全程 AI 自托管）

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| ANALYZE 后 | 直接进入 WRITE | 进入 GAP |
| GAP 产物 | 无 | _gap_analysis.md |
| GAP 之后 | 停住等用户 | 进 AUTO_REVIEW（自托管，不落断点） |
| 用户能看到的 | 不完整的模块列表 | 完整的缺失清单和评分 |

## 反模式 4：WRITE 阶段不加载模板直接写

### 现象

AI 在 WRITE 阶段直接凭经验写模块文档，没有加载 `templates/user-manual.md` 模板，导致产物结构不符合标准。

### 为什么是反模式

`templates/user-manual.md` 定义了模块文档的 8 项标准结构：
1. 模块概述
2. 权限说明
3. 操作入口
4. 前置条件
5. 详细操作步骤
6. 字段说明
7. 注意事项
8. 异常处理

不加载模板会导致章节缺失、格式不一致，后续 AUDIT 阶段会被阻断（流程图缺失/结构缺失/内容违规）。

### 正确做法

- WRITE 阶段开始前，AI 必须加载 `templates/user-manual.md`
- 按照模板的 8 项结构逐项填写
- 每模块完成后执行自检清单
- 如果包含流程图，使用 Mermaid 语法（不是 ASCII 文字画框）

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 模板加载 | 不加载，凭经验写 | 加载 user-manual.md |
| 章节结构 | 随意 | 8 项标准结构 |
| 审核通过率 | 低（被阻断） | 高（符合标准） |

## 反模式 5：REFINE 阶段不做一致性检查

### 现象

AI 在 REFINE 阶段只做逐模块的精炼补全，不执行交叉引用检查和术语一致性检查，就直接进入 INTEGRATE。

### 为什么是反模式

REFINE 阶段包含两个子步骤：
1. **精炼**：逐模块补全深度内容
2. **一致性检查**：术语统一 + 交叉引用验证

不做一致性检查会导致：
- 同一术语在不同模块写法不一致（如"用户"vs"操作员"）
- 模块间的交叉引用断裂
- 最终手册需要大量人工校对

### 正确做法

- 先完成所有模块的精炼（REFINE）
- 然后执行交叉引用检查（REFERENCE_CHECK）
- 产出 `_refine_log.md` 和 `_reference_check.md`
- 确保 100% 术语一致性和 100% 交叉引用有效

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| REFINE 后 | 直接 INTEGRATE | 进入 REFERENCE_CHECK |
| 术语一致性 | 不检查 | 100% 统一 |
| 交叉引用 | 可能断裂 | 全部有效 |

## 反模式 6：接力棒不更新就推进

### 现象

AI 完成一个阶段后，口头说"已完成了"，但实际上没有更新接力棒文件（`_baton.json`），导致状态记录与实际进度不一致。

### 为什么是反模式

接力棒是状态机的唯一真相来源。不更新接力棒的后果：
- 跨 Session 续跑时状态丢失，需要从头开始
- 无法确定当前阶段和已完成产物
- 多方协作时信息不同步

ManualGen 协议明确规定：**未更新接力棒 = 阶段未完成**。

### 正确做法

- 每个阶段完成后，立即读取接力棒 → 更新状态字段 → 标记产物 → 写回文件
- 接力棒模板参见 `protocols/baton-protocol.md`
- 每次回复结束时检查接力棒是否已更新

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 阶段完成 | 口头说"完成了" | 写回接力棒 |
| 跨 Session | 状态丢失 | 自动恢复 |
| 协议遵守 | 违反 | 严格遵守 |

## 反模式 7：隐私保护选择性执行

### 现象

AI 认为某些场景（如演示环境、测试数据）不需要严格遵守隐私保护规则，在产物中展示了真实密码、IP 地址或 API Key。

### 为什么是反模式

隐私保护是 **硬性阻断条件**，不是建议。所有产物必须遵守 `privacy/privacy-notice.md` 和 `SKILL.chunks/chunk-06-privacy-security.md` 的规定。

违反隐私保护的后果：
- 该阶段产物无效，必须重写
- AUDIT 阶段会扫描所有产物，发现即阻断
- 可能造成真实敏感信息泄露

### 正确做法

- 密码值 → 用 `****` 替代（配置项）或 `{密码}` 替代（文档示例）
- API Key / Token → 用 `{api_key}` `{token}` 替代
- 生产 IP/域名 → 用 `{服务器地址}` 替代
- 即使被用户要求展示敏感信息，也**不得展示**，应解释隐私保护政策

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 配置密码 | `password = "123456"` | `password = "****"` |
| API Key | `sk-xxxxxxxx` | `{api_key}` |
| 生产 IP | `192.168.1.100` | `{服务器地址}` |

## 反模式 8：AUTO_REVIEW 阶段不写完整明细（改 v6 命名）

### 现象

AI 在 AUTO_REVIEW 阶段只简单把决策状态推进，却没把「模块列表/流程图数量/缺失清单/完整性评分/决策类型①~④分布」写进 `_auto_decisions.md`，用户后续翻附录 C 时看不到任何支撑材料。

### 为什么是反模式

v6 虽然不需要等用户点「确认」，但决策必须全程可审计。只推进状态不写明细：
- 用户后续打开附录 C 时看不到 AUTO_REVIEW 的真实过程
- 如果 WRITE/TODO 结果不好，无法回溯 AUTO_REVIEW 的决策依据
- 违反 baton-protocol §5 「所有 AUTO_REVIEW 裁决必须持久化」

ManualGen 的 AUTO_REVIEW 规则明确要求：**必须把（模块列表 + 流程图数量 + 缺失清单 + 完整性评分 + 决策类型统计）完整写入 `_auto_decisions.md`**，并在 INTEGRATE 阶段汇总到附录 C。

### 正确做法

AUTO_REVIEW 阶段必须把以下内容原子写入 `_auto_decisions.md`：
1. **模块列表**：哪些模块将被生成文档（含模块数量）
2. **流程图统计**：各模块包含的流程图数量
3. **缺失清单**：已识别的功能缺失和待办项（同步写 `_todo_list.md`）
4. **完整性评分**：GAP 阶段的综合评分
5. **决策分布**：①置信传播 / ②补证据 / ③推断 / ④待复核 四类分别多少条（对应附录 C 概览表）
6. **Top 清单**：④类前 10 条（对应附录 C 第四大节）

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 展示内容 | "分析完成，请确认" | 模块+流程图+缺失+评分 |
| 用户判断 | 无法判断 | 清楚知道生成范围 |
| 修改机会 | 错过 | 在 WRITE 前可调整 |

## 反模式 9：WRITE 阶段跳过流程图绘制

### 现象

AI 在编写模块文档时只写文字描述，没有为每个核心功能绘制对应的 Mermaid 流程图。

### 为什么是反模式

流程图是用户手册的核心组成部分，它帮助用户直观理解操作路径。缺少流程图会导致：
- 用户只能通过文字理解操作步骤
- 复杂业务流程难以表达清楚
- AUDIT 阶段的"流程图质量"维度必然扣分

ManualGen 规则要求：流程图必须使用标准 Mermaid 语法，每个核心功能有对应流程图。

### 正确做法

- 每个核心功能至少一个流程图
- 使用 `flowchart TD` / `flowchart LR` / `stateDiagram-v2` 标准语法
- 节点文字使用 `「」` 而非 `""`（弯引号会破坏解析器）
- 流程图覆盖正常路径、驳回路径、终止路径

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 流程图 | 不画或画 ASCII 图 | Mermaid 标准语法 |
| 覆盖范围 | 无流程图 | 每个核心功能一个 |
| 审核结果 | 流程图质量 0 分 | 流程图质量满分 |

## 反模式 10：JUDGE 阶段跳过盲审直接判定 DONE

### 现象

AI 在 AUDIT 阶段完成自评后，不经过 JUDGE 阶段的子 Agent 盲审，直接标记为 DONE 输出最终手册。

### 为什么是反模式

JUDGE 阶段是 ManualGen 的**真正质量门**，由子 Agent 进行独立盲审（不与写作者共享上下文）。跳过盲审意味着：
- 自评可能遗漏问题（作者往往看不到自己的错误）
- 质量判定缺乏独立性
- 最终交付物可能存在未被发现的缺陷

ManualGen 的状态路由表明确规定：AUDIT → TODO_RESOLVE → JUDGE → DONE，**不可跳过**。

### 正确做法

- AUDIT 完成后，进入 TODO_RESOLVE 解决待办项
- TODO_RESOLVE 完成后进入 JUDGE
- JUDGE 阶段由子 Agent 盲审，产出 `_judgment.md`
- 盲审通过后标记为 DONE
- 如果盲审不通过，根据判定结果返回对应阶段修复

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| AUDIT 后 | 直接 DONE | AUDIT→TODO_RESOLVE→JUDGE→DONE |
| 质量判定 | 自评（有偏见） | 盲审（独立客观） |
| 质量保障 | 低 | 高 |

## 反模式 11：伪造接力棒（声称完成但产物不存在）

### 现象

接力棒 `_baton.json` 声称某层多批完成（如 L2=10 批、L3=14 批、L4=14 批 done），但对应产物目录 `_kb/L2_regions/`、`_kb/L3_functions/`、`_kb/L4_operations/` 根本不存在或为空；`_gap_analysis.md`、`_audit.md`、`_judgment.md` 等阶段报告一个都没有，却标记全部阶段 DONE。这是 v6.2 实测复现的最严重反模式（E:\test_agent 案例：手册仅 435 行、含 93 处技术泄漏，全部"通过"了自审）。

### 为什么是反模式

- 接力棒的全部意义就是"状态记录与磁盘产物一致"。产物不存在却声称完成 = 接力棒是谎言，断点续跑、闸门校验全部失效
- 跳层（L2-L4 全缺）意味着手册没有"页面分区→功能点→操作步骤"三层的实体内容，只剩 L0/L1 摘要，行数必然暴跌（几千行 → 几百行）
- 这是「AI 自审放水 + 计数手填」的叠加结果

### 正确做法（v6.3 机器校验）

- **接力棒所有计数由 `run.py baton_fix` 从磁盘反推**，AI 禁止手填 `*_batches_done` / `nodes_total`
- 每次声称某层完成前，必须运行 `'{"project_path":"<项目>"}' | python run.py verify`，输出 PASS 才可推进
- verify 输出 FAIL → 按 FAIL 清单回退补齐（产物缺失→补产物；计数不一致→baton_fix 反推）
- 每批落盘后立即运行 verify，不等整层跑完

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 层完成判定 | AI 口头宣布 + 手填计数 | `run.py verify` PASS + `baton_fix` 反推 |
| 产物与接力棒 | 接力棒写什么算什么 | 磁盘反推为准，不一致即 FAIL |
| 检测手段 | 无（只能靠自觉） | 机器校验，AI 无法伪造 |

## 反模式 12：自评放水（AI 自审自己的产物并放自己过）

### 现象

G0-G5 闸门、GW 去技术化检查、AUDIT 十维评分、REFINE 子 Agent 复检，全部是"AI 检查自己的产物"。AI 在长流程中几乎不会判自己不合格——E:\test_agent 手册含 93 处 API 端点/数据库名/参数名，AUDIT 的"内容合规性"检查却通过；L2/L3/L4 目录为空，闸门却全部放行。

### 为什么是反模式

- LLM 自评存在系统性偏向：为了完成任务，会倾向"宣布通过"而非"发现自己的问题"
- 自审和被审是同一个上下文，无法提供独立视角（这正是 JUDGE 设计子 Agent 盲审的原因）
- 凡是"可客观判定"的事（文件在不在、数字对不对、有没有 API）都让 AI 自述，等于让球员当裁判

### 正确做法（v6.3 强/软约束分层）

- **强约束（机器判定）**：文件存在性、批次计数、技术泄漏、覆盖完整性 → 全部交给 `run.py`，AI 无权豁免退出码
- **软约束（AI 判定）**：内容质量、功能识别、置信度裁决 → AI 保留
- 阻断性检查中标 ⚙ 的项（内容合规性→scan_tech、覆盖完整性⑪→coverage、产物真实性→verify）禁止用"我已检查过"代替脚本输出

### 对比

| 维度 | 错误做法 | 正确做法 |
|------|-----------|-----------|
| 产物检查 | AI 说"我检查过了" | `run.py` 脚本输出为准 |
| 判定权 | 全在 AI | 可判定的事归机器，智力活归 AI |
| 放水空间 | 大 | 无（脚本不偏袒） |

## 反模式 13：技术泄漏进用户手册（API 端点/参数名写进手册正文）

### 现象

最终手册通篇出现 `POST /api/knowledge-base/`、`chunk_size=1000`、`top_k`、`max_hops`、`temperature`、`SQLite`、`Neo4j` 等，甚至自创"附录 A：常用 API 速查"。用户（运营/客服/销售）完全看不懂，手册从"用户操作手册"变成了"开发文档摘要"。

### 为什么是反模式

- ManualGen 定位是**用户版操作手册**（面向运营/销售/客户），不是 API 文档。技术参数对目标用户毫无意义
- 根因：主控在 L0-L5 接触了大量技术内容，如果 WRITE 阶段由主控自己写（而非隔离上下文的子 Agent），技术信息必然泄漏
- GW 闸门（禁止 API 端点）在 v6.2 由 AI 自检，必然放水

### 正确做法（v6.3 机器扫描）

- WRITE 必须由隔离上下文的子 Agent 写 `output_user_manual/_modules/*.md`（主控不得直接写最终手册）
- INTEGRATE 强制由 `_modules` 合并，`_modules` 不存在即阻断
- 模块文档和最终手册必须过 `'{"project_path":"<项目>","manual_path":"<文件>"}' | python run.py scan_tech`，**P0 命中数必须为 0**，命中即打回 REFINE 重写
- 手册只写：界面长什么样 → 用户点什么 → 填什么 → 看到什么

### 对比
