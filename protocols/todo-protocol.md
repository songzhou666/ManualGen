# ManualGen TODO 标记规范与生命周期协议（v6 全自主版）

> 定义统一的 TODO 标记格式、收集机制和解决流程。
> v6 变更：TODO_RESOLVE 全自主解决（AI 自主决策，不询问用户，与 chunk-05 §TODO 规则矩阵 T1~T6 对齐）；来源阶段从 v5 的 EXPLORE/EXTRACT/ANALYZE 调整为六层 + 图谱阶段。

---

## 一、TODO 标记规范

### 1.1 标记格式

所有阶段在产出物中遇到无法即时解决的问题时，必须使用以下 HTML 注释格式标记：

```markdown
<!-- TODO:[类型] [描述] | 来源: [阶段/模块] | 依赖: [待解决条件] -->
```

**示例**:
```markdown
<!-- TODO:INFO_GAP 技术支持联系方式和业务咨询联系方式需从运维文档获取 | 来源: 用户版模板-第8节 | 依赖: 运维文档审阅完成 -->
<!-- TODO:CROSS_REF 模块A引用了模块B的[操作步骤]字段说明，模块B尚未编写 | 来源: 模块A-WRITE阶段 | 依赖: 模块B文档完成 -->
<!-- TODO:PLACEHOLDER 系统登录界面截图需人工截取 | 来源: 快速入门-截图占位 | 依赖: 人工介入 -->
<!-- TODO:DEP_PENDING 学院创建前必须先创建负责人，但负责人模块的依赖关系尚未确认 | 来源: GAP阶段 | 依赖: 负责人模块分析完成 -->
```

### 1.2 TODO 类型

| 类型 | 代码 | 说明 | 默认解决方式 |
|------|------|------|-------------|
| 信息缺口 | INFO_GAP | 需要从其他文档/模块获取的信息 | TODO_RESOLVE 阶段自动提取 |
| 跨模块引用 | CROSS_REF | 引用了尚未编写的其他模块内容 | TODO_RESOLVE 阶段等待 |
| 占位内容 | PLACEHOLDER | 截图、示例数据等需人工补充 | 标记 MANUAL，需用户处理 |
| 依赖待定 | DEP_PENDING | 上下游关系不确定、依赖未就绪 | TODO_RESOLVE 阶段重分析 |
| 配置缺失 | CONFIG_MISSING | 系统配置参数、连接信息等未知 | TODO_RESOLVE 阶段 AI 推断加警告标注，推断不了列附录 C |

### 1.3 标记时机

| 阶段 | 可能产生 TODO 的场景 |
|------|---------------------|
| L0_SKELETON | 识别到的模块但无代码路径 |
| L1~L4 | 模块/页面/功能/操作提取不完整 |
| L5_DETAIL | 字段/权限/按钮状态提取不完整 |
| GRAPH_BUILD | 图谱构建时发现断链、低置信节点 |
| GAP_ANALYSIS | 识别到缺失但已标记 |
| WRITE | 截图占位、跨模块引用、联系方式 |
| INTEGRATE | 交叉引用断裂、目录缺失模块 |
| AUDIT | 审核发现的需补充项 |

## 二、TODO 收集机制

### 2.1 收集时机

每个阶段**完成时**，AI 必须扫描当前阶段产出的所有文件内容，提取 `<!-- TODO:` 标记。

### 2.2 收集方式

使用正则表达式匹配：
```
/\<\!--\s*TODO:(\w+)\s+(.+?)\s*\|\s*来源:\s*(.+?)\s*\|\s*依赖:\s*(.+?)\s*--\>/g
```

### 2.3 汇总到 _todo_list.md

每次收集后，追加或更新 `_todo_list.md`：

```markdown
# TODO 列表

| ID | 类型 | 描述 | 来源 | 依赖 | 状态 | 收集阶段 |
|----|------|------|------|------|------|----------|
| T-001 | INFO_GAP | 技术支持联系方式 | 用户手册-第8节 | 运维文档审阅完成 | PENDING | WRITE |
| T-002 | PLACEHOLDER | 系统登录截图 | 快速入门 | 人工截图 | PENDING | WRITE |
```

**规则**:
- 新 TODO 追加到列表末尾
- 已有 TODO 重复出现 → 合并去重（以描述+来源为唯一键）
- TODO 被解决后 → 状态改为 RESOLVED，记录解决阶段

### 2.4 更新规则

每次阶段完成后执行：
```
1. 读取已有 _todo_list.md（如果存在）
2. 扫描当前阶段产物中的 <!-- TODO: 标记
3. 去重合并：新 TODO 追加，已有 TODO 保留
4. 检查已解决的 TODO（被引用内容已存在）
5. 写入更新后的 _todo_list.md
```

## 三、TODO_RESOLVE 阶段

### 3.1 阶段定位

在 AUDIT 和 JUDGE 之间新增 **TODO_RESOLVE** 阶段：

```
... → AUDIT → TODO_RESOLVE → JUDGE → DONE
```

### 3.2 执行流程

```
Step 1: 读取 _todo_list.md
Step 2: 对每个 PENDING 状态的 TODO 进行分类处理（AI 全自主，不询问用户）
Step 3: 可自动解决 → 执行解决操作（按 chunk-05 §TODO 规则矩阵 T1~T6）
Step 4: 无法自动解决但可推断 → 按 chunk-05 §TODO 熔断规则降级（推断加警告标注 / 附录C列示）
Step 5: 需人工介入 → 标记 MANUAL（仅最终报告汇总给用户，不中断流程）
Step 6: 无法解决且影响质量 → 标记 BLOCKER（附录 C Top 清单，不阻断 DONE）
Step 7: 更新 _todo_list.md（原子写）
Step 8: 输出 _todo_resolution.md（解决报告）
```

### 3.3 TODO 分类处理

| TODO 当前状态 | 处理策略 | 新状态 | 说明 |
|-------------|----------|--------|------|
| PENDING | 检查依赖条件是否满足 | 见下表 | 按依赖条件判断 |
| RESOLVED | 跳过，不做处理 | RESOLVED | 已解决 |
| MANUAL | 汇总清单，输出给用户 | MANUAL | 需人工处理 |
| BLOCKER | 判定是否需要阻断 | BLOCKER / SKIP | 影响质量的设为阻断 |

### 3.4 依赖条件判断

| 依赖类型 | 判断方法 | 满足条件时的处理 | 不满足时的处理（AI 全自主） |
|----------|----------|-----------------|---------------|
| 运维文档审阅完成 | 检查 `_integration.md` 是否包含联系方式s | 从整合文档提取填充 | → 附录 C 列 BLOCKER（标注需运维补充），不中断流程 |
| 模块X文档完成 | 检查 `output_user_manual/_modules/` 是否包含模块X | 从模块文档提取引用 | → 标记 BLOCKER（降低评分），附录 C 列示 |
| 人工截图 | 无法自动判断 | → 标记 MANUAL（最终汇总给用户） | → 标记 MANUAL |
| 负责人模块分析完成 | 检查 `_kb/L1_modules/` 或 graph 中是否有负责人模块节点 | 补充依赖关系 | → 标记 BLOCKER，附录 C 列示 |

### 3.5 输出 _todo_resolution.md

```markdown
# TODO 解决报告

## 基本信息
- 解决时间: {ISO 8601}
- 来源: _todo_list.md

---

## 解决结果汇总

| 结果 | 数量 | 说明 |
|------|------|------|
| 自动解决 | {N} | 已自动填充到对应位置 |
| AI 推断 | {N} | AI 按规则推断补全，文档中已标注 |
| 需人工介入 | {N} | 截图/配置等需人工完成（仅汇总告知，不中断流程） |
| 无法解决 | {N} | 列附录 C，不阻断 DONE |

---

### 自动解决
| ID | 描述 | 填充位置 | 填充内容摘要 |
|----|------|----------|-------------|
| T-001 | {描述} | {文件路径} | {摘要} |

### AI 推断
| ID | 描述 | 推断值 | 依据 |

| T-002 | {描述} | {推断值} | {推断依据（同类字段/角色继承等）} |
```

## 四、TODO 对判定的影响

### 4.1 对 AUDIT / JUDGE 评分的影响

| TODO 解决情况 | 评分影响 |
|--------------|----------|
| 所有 TODO 已解决 | 无影响 |
| 有 MANUAL（人工）TODO | AUDIT 相应维度扣 2 分参考（仅汇总告知，不中断流程） |
| 有 BLOCKER TODO | JUDGE 对应模块扣 5 分参考 + 附录 C Top 清单列示 |

### 4.2 发布条件（v6：AI 自主，BLOCKER 不阻断 DONE）

- 无 BLOCKER TODO → 正常推进 JUDGE
- 有 BLOCKER TODO → 不阻断 DONE，附录 C 列示 + 受影响模块 JUDGE 评分扣 5 分参考（模块仍可 交付）
- 所有 TODO 数量 > 5 且未解决 > 3 → AUDIT 阶段给出全局提示，不自动回退

## 五、用户版模板第 8 节处理规则

### 5.1 TODO 标记模板

用户版模板第 8 节必须写为：

```markdown
## 8. 遇到问题找谁？

<!-- TODO:INFO_GAP 技术支持联系方式和业务咨询联系方式需从运维/系统配置文档获取 | 来源: 用户版模板-第8节 | 依赖: 运维文档审阅完成 -->

> 联系方式将在 TODO_RESOLVE 阶段统一处理。如您有联系方式，请在此补充。
>
> | 类型 | 联系方式 |
> |------|----------|
> | 技术支持 | (待补充) |
> | 业务咨询 | (待补充) |
```

### 5.2 解决时机

1. WRITE 阶段 → 写入 TODO 标记 + 占位内容
2. INTEGRATE 阶段 → 检查其他模块文档是否包含联系方式
3. TODO_RESOLVE 阶段 → 从整合文档提取联系方式
4. 提取失败 → 附录 C 列 BLOCKER（AI 自主，不中断流程）

### 5.3 跨文档提取策略

在 TODO_RESOLVE 阶段，检查以下位置是否包含联系方式信息：
- 系统配置文件（如 `application.yml` 中的联系人字段）
- 已有模块文档中的"技术支持"章节
- `_exploration.md` 中的项目信息

### 5.4 隐私与TODO的关系
- TODO 标记本身不得包含敏感数据（账号、密码、token等）
- 如果TODO内容涉及敏感信息，参照 `SKILL.chunks/chunk-06-privacy-security.md` 的脱敏规则处理
- 联系方式类TODO的填充内容必须脱敏后写入文档

---

## 六、与条件性跳过的关系

在 TODO_RESOLVE 阶段之后实施的条件性跳过机制中：
- 如果 `_todo_list.md` 为空（无任何 TODO）→ 可跳过 TODO_RESOLVE
- 如果所有 TODO 均为 PLACEHOLDER → TODO_RESOLVE 仅做汇总输出，不阻塞
